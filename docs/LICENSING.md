# Licensing and telemetry

SPYDIR is free. It is activated with a licence key so that there is a count of who is using it and
somewhere for paid capability to attach later — not to police a read-only directory reader. That
purpose decides almost every design choice below, and it is why an overdue check degrades to a
warning rather than a locked door (`shared/license.ts:1-8`).

Two subsystems are described here: the licence — key format, signup, activation, recovery — and
telemetry, which is adjacent, opt-in, and off by default.

Packaging, version bumping and the update feed live in [RELEASING.md](./RELEASING.md). The version
string the licence check reports is the one from `package.json`, bumped as described there.

## The key

A key looks like this:

```
SPYDIR-4PEH4-M9TFA-A37EB-ZZ3DB
```

A fixed prefix and four groups of five characters, generated by `newKey` in
`site/lib/server/keys.ts:13`. The body is 20 characters drawn from Crockford base32
(`site/lib/server/keys.ts:11`):

```
0123456789ABCDEFGHJKMNPQRSTVWXYZ
```

`I`, `L`, `O` and `U` are absent, which is what makes it Crockford's alphabet rather than plain
base32. The first three go because a key is read aloud, written on a whiteboard and retyped from a
screenshot, and `I`/`1`, `L`/`1` and `O`/`0` are the pairs people get wrong; `U` goes, in Crockford's
design, so that a generated string cannot spell an obscenity by accident.

Note that the excluded letters are *rejected*, not corrected. Crockford's own specification folds
`I` and `L` to `1` and `O` to `0` on input; SPYDIR does not. A key typed with a letter O in place of
a zero fails the shape check (`shared/license.ts:86`) and the person is told the shape is wrong
rather than being silently given a different key.

**Entropy.** 20 characters from a 32-character alphabet is 20 × 5 = **100 bits**. The draw is
uniform: `randomBytes(20)` is reduced with `b % 32`, and 256 is an exact multiple of 32, so there is
no modulo bias. At 100 bits, guessing a key is not an attack that exists, which is why the server
can answer a bare "is this key real?" question at all. `key_hash` is `UNIQUE`
(`site/lib/server/store.ts:40`) and `issueKey` still retries on a collision
(`site/lib/server/licences.ts:32`) — not because a clash is expected, but because losing that race
in front of someone signing up should not surface as an error.

### `normalizeKey`, and why there are two of it

Keys arrive by email and, often enough, out of a PDF or a web page. They arrive with a line break in
the middle where the mail client wrapped, with non-breaking spaces where a browser rendered them,
lowercased, or with the dashes and prefix stripped by whatever pasted them. All of those are the
same key, and `normalizeKey` (`shared/license.ts:67`) is what makes them the same string: everything
outside `[0-9A-Z]` is dropped, the prefix is removed if present, the first 20 characters are
regrouped into fives, and the prefix is put back.

| Input | Canonical form |
| --- | --- |
| `spydir-4peh4-m9tfa-a37eb-zz3db` | `SPYDIR-4PEH4-M9TFA-A37EB-ZZ3DB` |
| `SPYDIR-4PEH4-M9TFA-\nA37EB-ZZ3DB` | `SPYDIR-4PEH4-M9TFA-A37EB-ZZ3DB` |
| `SPYDIR4PEH4M9TFAA37EBZZ3DB` | `SPYDIR-4PEH4-M9TFA-A37EB-ZZ3DB` |
| `4PEH4M9TFAA37EBZZ3DB` | `SPYDIR-4PEH4-M9TFA-A37EB-ZZ3DB` |

**Both implementations must stay identical.** The app's copy is `shared/license.ts:67`; the server's
is `site/lib/server/keys.ts:27`, and the two function bodies are currently byte-for-byte the same —
only the doc comment above them differs. This is not tidiness. The server stores
`sha256(normalizeKey(key))` (`site/lib/server/keys.ts:35`) and looks a key up by that hash at
activation (`site/app/api/activate/route.ts:50`). If the two normalisers ever disagreed about what
a key is — about a stray character, about the 20-character truncation, about the prefix — then a
key pasted one way would hash to a row that exists and pasted another way would hash to nothing, and
the failure would look like "that key is not recognised" rather than like a bug.

The same reasoning is why the activation response is signed over `normalizeKey(key)` rather than
over whatever was posted (`site/app/api/activate/route.ts:75-79`). The app re-posts what it was
signed, so signing a non-canonical spelling would put a key into circulation that stops matching the
database the moment a client sends it without dashes.

Two smaller helpers sit beside it. `tidyKeyInput` (`shared/license.ts:75`) strips whitespace and
uppercases without regrouping, which is safe to run on every keystroke — it cannot move the caret
out from under someone mid-edit. Full normalisation runs on blur instead
(`src/workspaces/Activate.tsx:84`, `src/workspaces/Settings.tsx:597`). `keyHint`
(`shared/license.ts:79`) masks all but the last group for display: `SPYDIR-•••••-•••••-•••••-ZZ3DB`.

## Signing up

The website asks for an address, emails a six-digit code, and sends the key once the code comes
back. The UI is `site/components/Subscribe.tsx`; the sequence is:

1. **`POST /api/signup` `{ email }`** (`site/app/api/signup/route.ts:22`). The address is validated
   and folded (below). A verification code is created, hashed and stored, and emailed. The reply is
   `200 { status: 'sent', expiresInMinutes: 10 }`. Failure modes: `400` for a malformed address,
   `429` for the per-IP limit (10/hour) or the per-address send cap, `503` when no mail provider is
   configured or the global cap of 5,000 new licences in 24 hours has been hit
   (`site/app/api/signup/route.ts:25-43`), `502` when the send itself fails. **No key is issued at
   this step.**
2. **The code email** (`site/emails/verifyCode.ts`). The code is in the subject line as well as the
   body, because a six-digit number is the entire content of the message and most people read it
   from the notification.
3. **`POST /api/verify` `{ email, code }`** (`site/app/api/verify/route.ts:24`). The code is checked
   and consumed. On success the address either gets a newly issued key or the one it already owns,
   and that key is **emailed, never returned** (`site/app/api/verify/route.ts:67`). The reply is
   `200 { status: 'ok', hint, reissued }`, where `hint` is `SPYDIR…ZZ3DB` — enough to confirm the
   right key arrived, not enough to use.
4. **The key email** (`site/emails/licenceKey.ts`). Identical whether the key was just issued or
   re-sent, deliberately: a "here it is again" variant would disclose the very fact the recovery
   endpoint works to keep quiet.
5. **The app**: the person enters the key and it is activated (next section).

### What the verification step fixes

Before it existed, `/api/signup` issued the key directly, and it is worth being clear about what
that cost (`site/lib/server/otp.ts:6-16`, `site/app/api/signup/route.ts:12-21`):

- It **disclosed registration**. The endpoint answered `409 "that address already has a key"`, so
  anyone could ask it which addresses use SPYDIR.
- It let a stranger **take someone else's only key**. One key per address is enforced by the
  database, so typing a colleague's or a competitor's address consumed the single key that address
  would ever be given, and left the real owner unable to sign up for something they never received.

Proving the address is readable closes both, and makes the two cases indistinguishable from outside:
every `/api/signup` request now gets the same reply.

### Addresses are folded

`foldEmail` (`site/lib/server/guard.ts:87`) normalises to NFKC, lowercases, and drops any `+` tag, so
`Ada+spydir@Example.com` and `ada@example.com` are one address. Without that, a single mailbox could
hold as many keys as it cared to ask for, and "one key per address" would mean nothing.

### The verification code

All of this lives in `site/lib/server/otp.ts`.

| Property | Value | Why |
| --- | --- | --- |
| Length | 6 digits (`:18`) | Readable from a notification; `randomInt` is rejection-sampled, so there is no modulo bias (`:41`) |
| TTL | 10 minutes (`:19`) | Long enough for a slow mail hop, short enough that a stolen code is usually dead |
| Wrong guesses | 5 per challenge (`:21`) | Six digits is a million possibilities; five guesses against one live challenge is not an attack |
| Sends per address | 5 while a challenge is live (`:23`) | Bounds a mail-flood against one mailbox |
| Storage | `sha256(pepper:email:code)` (`:34`) | The code itself is never stored, and mixing the address in means a stolen hash cannot be replayed against a different one |

Codes are short-lived and low-entropy by nature, so what makes them safe is the attempt cap rather
than the code. Two further rules follow from that. Asking again **replaces** the live challenge
rather than adding a second (`site/lib/server/otp.ts:63`) — two live codes double the guessing
surface, and leave the reader guessing which of two emails is current — while the *send* counter
survives the replacement, so repeated asking is still bounded. And a code is consumed whether or not
it was right (`site/lib/server/otp.ts:99`): a correct one deletes the row, and a wrong one deletes it
once the cap is reached, so a challenge cannot be ground down. `pruneCodes`
(`site/lib/server/otp.ts:124`) clears expired rows.

### Why keys are encrypted rather than hashed

`key_hash` is what activation looks up, but the key itself is also stored, encrypted, in `key_enc`
(`site/lib/server/secret.ts`). Hashing alone was the safer instinct and it made "I lost my key"
unanswerable: with one key per address and no way to read it back, losing it would lock someone out
of a free product permanently. A licence key is not a password and not a payment credential, and
being able to re-send one to the address that owns it is worth more than the marginal gain of a
one-way hash.

The stored value is versioned:

| Format | Layout | Key derivation |
| --- | --- | --- |
| Legacy (3 parts) | `iv.tag.body` | one pass of SHA-256 over the secret (`site/lib/server/secret.ts:26`) |
| `v2` (5 parts) | `v2.salt.iv.tag.body` | scrypt, N=2¹⁵, r=8, p=1, per-record salt (`site/lib/server/secret.ts:37`) |

Both are AES-256-GCM. The legacy derivation is kept only to read old rows: a single hash is not a key
derivation function, and if an operator had ever set something memorable as `LICENSE_SECRET`, the
`key_enc` column — plaintext licence keys for every user — would become an offline guessing target at
billions of attempts per second. The per-record salt keeps rows independent: one cracked record says
nothing about the next, and nothing can be precomputed across the table. `isLegacyFormat`
(`site/lib/server/secret.ts:69`) exists so a legacy row can be rewritten the next time it is touched.
Rows written before `key_enc` existed at all cannot be recovered and have to be reissued by hand
(`site/lib/server/licences.ts:53-61`, `site/app/api/verify/route.ts:58-65`).

### One live key per address

Enforced by a partial unique index rather than by remembering to check
(`site/lib/server/store.ts:50`):

```sql
CREATE UNIQUE INDEX IF NOT EXISTS licence_email_live ON licence (email) WHERE revoked = 0;
```

The `WHERE revoked = 0` is what makes it usable: a revoked row stays for the record without blocking
a replacement. Asking again does not issue a second key and does not revoke the first — revoking in
that moment would break the very installation someone is trying to get working
(`site/lib/server/licences.ts:6-13`).

One detail worth knowing before editing `issueKey`: SQLite names the *column* in a unique-constraint
error, never the index, so the conflict has to be detected by matching on `licence.email`, not on
`licence_email_live` (`site/lib/server/licences.ts:40-48`).

## Activation

The desktop app posts the key and gets back a signed payload it can cache.

**Sent** (`electron/license.ts:132-136`):

| Field | Value |
| --- | --- |
| `key` | the canonical key |
| `machine` | `sha256(hostname \| platform \| arch \| userData path)` — hashed on the client, so the raw values never leave the machine (`electron/license.ts:76`) |
| `version` | the app version |
| `os` | `process.platform` |

The server hashes `machine` *again* with a server-side pepper before storing it
(`site/app/api/activate/route.ts:58-70`): enough to count installs, not enough to identify a
computer. The row is `(licence_id, machine)` with `first_seen`, `last_seen` and a `count`, so
repeated activations from one machine update rather than accumulate.

**Signed** (`site/app/api/activate/route.ts:75-86`, shape at `shared/license.ts:26`): `key`, `email`,
`tier`, `features`, `expiresAt`, `issuedAt`, and `notAfter`, which is `issuedAt + 30 days`
(`site/app/api/activate/route.ts:12`). `signPayload` (`site/lib/server/keys.ts:69`) signs the JSON
with Ed25519 and returns `{ payload, signature }`, both base64.

**Cached** (`electron/license.ts:88-92`): `{ payload, signature, checkedAt }` written to
`licence.json` in Electron's `userData` directory, via a temp file and a rename, with mode `0600`;
the directory itself is created `0700` if missing (`electron/license.ts:33-37`).

**Verified locally** (`electron/license.ts:59`). The app holds the public half of the signing key at
`resources/license-public.pem`, shipped into a packaged build through `extraResources`
(`electron-builder.yml:38`) and found in development by searching the checkout
(`electron/license.ts:40-49`). The cached payload is base64-decoded and checked against the signature
with `crypto.verify(null, …)` before being parsed. Signing means the cache can be trusted for weeks
without asking again, and — more to the point — that a `hosts` entry pointing the app at something
else cannot mint a licence.

If there is no public key, verification **refuses** rather than trusting. The cache file is plain
base64 JSON in the user's own home directory; failing open would make that file authoritative about
tier and features, which is exactly backwards. The two failures are reported differently, because one
is a build problem the user can do nothing about and the other is a licence that does not match its
signature (`electron/license.ts:96-108`); `canVerify` (`electron/license.ts:218`) is what tells them
apart, and it is also reported in the app's About information (`electron/main.ts:311`).

Generate the pair with `site/scripts/keygen.mjs`: the private half goes in `LICENSE_PRIVATE_KEY`, the
public half is committed as `resources/license-public.pem`. `GET /api/pubkey`
(`site/app/api/pubkey/route.ts`) serves the public half so a build can be given the right one, and
says whether the server is running on an ephemeral pair generated at boot — publishing it is the
point, since it verifies signatures and cannot make them.

### Status

`statusOf` (`shared/license.ts:92`) derives the status from the signed payload and the current time.
There are four (`shared/license.ts:10-18`), and **`GRACE_DAYS` is 21** (`shared/license.ts:54`).

| State | Meaning |
| --- | --- |
| `none` | No key on this machine |
| `active` | Checked recently and good |
| `grace` | The check is overdue and the server could not be reached. Everything works |
| `lapsed` | Overdue well past grace, the licence itself expired, or the server withdrew the key |

Transitions, given `notAfter = issuedAt + 30 days` and a 21-day grace window:

| Situation | Status | Notes |
| --- | --- | --- |
| Freshly activated | `active` | Good for 30 days without contacting anything |
| Re-check falls due, server reachable | `active` | A fresh signed payload replaces the cache (`electron/license.ts:202`) |
| Re-check falls due, server unreachable, ≤ 21 days overdue | `grace` | The previous payload stays cached; the failure is carried as `message` (`electron/license.ts:199`) |
| Re-check falls due, server unreachable, > 21 days overdue | `lapsed` | `now > notAfter + 21 days` (`shared/license.ts:96-97`) |
| `expiresAt` reached | `lapsed` | Checked first, so it wins even when `notAfter` is still in the future (`shared/license.ts:93`) |
| Server withdrew the key (`403`) or does not know it (`404`) | `lapsed` **immediately** | Grace is for a machine that cannot reach the server, not for a key the server has answered about (`electron/license.ts:192-198`) |
| Machine offline for a year | `lapsed` | 30 days valid plus 21 days grace, then lapsed — and still fully usable |
| Cached payload fails signature verification | `lapsed` | With a message distinguishing a bad signature from a build that cannot verify (`electron/license.ts:96-108`) |
| Key removed in Settings | `none` | The cache file is deleted (`electron/license.ts:207`) |

Two things follow from that table.

**Only `none` locks.** The key screen appears when `licence.status === 'none'` **and** the open
snapshot is not the sample fixture (`src/App.tsx:49`). In practice that is:

- a fresh install with no `licence.json`;
- after **Deactivate** in Settings, even with a directory open — the licence comes off the machine,
  the session ends, and nothing on disk is touched, so the saved session and the timeline are still
  waiting when a key comes back (`src/state.tsx:172-181`);
- when a cache file cannot be read or parsed at all (`electron/license.ts:80-86`), or an activation
  attempt returned an unlicensed state.

It does not appear for `grace` or `lapsed`; those keep the full app and say so in Settings. It does
not appear when the sample directory is open, which needs no key at all. And it does not block
**Settings** or the **guide**, which are reachable while locked because the check order in
`src/App.tsx:51-54` puts them first — someone who cannot activate can still read what the app does
and change its settings.

**What lapsing actually costs** is `hasFeature` returning `false` (`shared/license.ts:100`). Nothing
gates on features today, so at present a lapsed licence costs a line of text in Settings.

### When the re-check happens

`refreshLicence` (`electron/license.ts:184`) runs once, eight seconds after the app is ready
(`electron/main.ts:374`), out of the way of first paint. It reads the cache, verifies it, and
**returns immediately if the status is still `active`** (`electron/license.ts:189`) — so a running
install contacts the licence server only on the first launch after the 30 days have elapsed. That is
what "roughly monthly" means; there is no background poll and no timer that fires mid-session. A
machine left running for months will not re-check until it is next started.

Failure is not an error anyone needs to see. The status drifts to `grace`, the app carries on, and
Settings explains it (`src/workspaces/Settings.tsx:550-560`, `shared/license.ts:105`).

The endpoint is chosen at `electron/endpoints.ts:17`: production for a packaged build,
`http://localhost:4200` in development, overridable by `SPYDIR_LICENSE_API` **only** in development.
The override is ignored once packaged, because anything that can set an environment variable could
otherwise point activation and telemetry at a host of its choosing.

## Recovery

`POST /api/recover` `{ email }` (`site/app/api/recover/route.ts:25`, UI at
`site/components/RecoverKey.tsx`) re-sends an existing key to the address that owns it.

The reply is always `202 { status: 'If that address has a key, it is on its way.' }`. Anything else
turns the endpoint into a way of asking which addresses use SPYDIR — and, because the key would then
be obtainable by anyone who knows an address, into a way of taking a licence. The key is only ever
delivered by email, never in the response.

"Identical" has to include failures and timing, which is the part that is easy to get wrong. A
decrypt failure or a mail-send failure can only happen for an address that *is* registered, so
letting either surface would mean `500` for known addresses and `202` for unknown ones — the same
enumeration oracle, arrived at from the other direction. Everything below the address check is
therefore wrapped in a `try`, and the send is deliberately **not awaited**, so the response does not
take measurably longer for an address that exists
(`site/app/api/recover/route.ts:11-23`, `:40-70`). The operator learns about failures from the log,
which is the only place that can safely say more.

Rate limit: 10 per IP per hour.

## Reserved keys

Thirty keys are not issued by the signup form at all. They are seeded by
`site/scripts/reserved-keys.mjs` and handed out directly (`:22-25`):

| Kind | Count | Tier | Features |
| --- | --- | --- | --- |
| `developer` | 10 | `enterprise` | `scheduled-reports`, `multi-domain`, `write-operations`, `team-sync`, `priority-support` |
| `beta` | 20 | `team` | `scheduled-reports`, `multi-domain` |

Each is inserted against a synthetic address, `developer-01@reserved.spydir` through
`beta-20@reserved.spydir`, with `note = 'reserved:<kind>'`. Seeding is idempotent: a label that
already has a live row is left alone (`site/scripts/reserved-keys.mjs:97-100`). The rows carry
`key_hash` but **no `key_enc`**, so reserved keys cannot be read back out of the database and
`/api/recover` will never send one.

That is why the script writes them to a file. The output is a plain-text listing encrypted with
AES-256-GCM under a scrypt-derived key (N=2¹⁷, r=8, p=1) and wrapped in a small JSON envelope tagged
`spydir-reserved-keys/1`, written to `keys/reserved-keys.enc` or wherever `KEYS_FILE` points
(`site/scripts/reserved-keys.mjs:59-77`).

```bash
KEYS_PASSPHRASE=… node scripts/reserved-keys.mjs seed   # generate, insert, write the file
KEYS_PASSPHRASE=… node scripts/reserved-keys.mjs read    # print it back
```

**The passphrase rule: `KEYS_PASSPHRASE` is never written anywhere** — not into the file, not into
the database, not into this repository (`site/scripts/reserved-keys.mjs:6-16`). The script refuses to
run without it and says so. Losing it means the file cannot be opened and the only remedy is
reseeding, because the database holds hashes and nothing else. Keep the file and the passphrase
somewhere that outlives the laptop that made them, and keep them apart.

Activation treats these exactly like any other key: the tier and feature list come from the row, so a
developer key produces a signed payload with `tier: 'enterprise'` and five features on it.

## Telemetry

**Opt-in, and off by default** — `DEFAULT_SETTINGS.privacy.telemetry` is `false`
(`shared/settings.ts:161`). Nothing is sent until someone turns it on in
**Settings ▸ Privacy & session**.

Exactly these fields are sent (`shared/telemetry.ts:12-26`):

| Field | What it is |
| --- | --- |
| `install` | A random UUID per installation, kept in settings so clearing them resets it (`electron/telemetry.ts:31`). Not a machine id, and unrelated to the activation `machine` hash |
| `version` | App version |
| `os` | `process.platform` |
| `arch` | `process.arch` |
| `workspacesUsed` | Which workspaces were opened this run — names only, deduplicated and sorted |
| `domainCount` | How many directories are open, not which |
| `objectsBucket` | Users + groups + computers + OUs, as a range |
| `findingsBucket` | Hygiene findings, as a range |
| `reportsGenerated` | A count |
| `sessionMinutesBucket` | Session length, as a range |

Counts are reported as ranges — `0`, `1-99`, `100-999`, `1k-10k`, `10k-100k`, `100k+`
(`shared/telemetry.ts:29`), and `0-5`, `5-30`, `30-120`, `120+` minutes
(`shared/telemetry.ts:38`) — because an exact object count is close to an organisation's
fingerprint. There is no field for a domain, a DN, an account, a group or a hostname, and none of
those pass through `buildPayload` at any point.

**Three layers keep directory data out of it.**

1. **Construction.** `buildPayload` (`shared/telemetry.ts:57`) takes only a `UsageFacts` record, and
   the one directory-shaped input it accepts is `snapshot.stats` — from which it reads numbers and
   throws the rest away. Nothing identifying can reach the payload because nothing identifying is
   passed in.
2. **The allow-list on the way out.** `sanitize` (`shared/telemetry.ts:90`) rebuilds the object from
   `ALLOWED_KEYS` (`:76`) and drops everything else, and `currentPayload`
   (`electron/telemetry.ts:52`) runs it on every payload. This is defence against a future careless
   edit rather than against today's code.
3. **The allow-list on the way in.** `POST /api/telemetry` (`site/app/api/telemetry/route.ts:78`)
   **rejects** a payload carrying any unexpected key with a `400`, and `tidy` (`:37`) rebuilds each
   allowed value to a known type and size — strings truncated, counts clamped to 0…1,000,000, the
   workspace array capped at 16. The size clamping matters on its own: an allowed key holding fifty
   megabytes used to be stored as it arrived, and a full disk stops activation working for everyone,
   which turns an anonymous counter into a way of taking the service down.

**Inspecting it before it is sent.** Settings ▸ Privacy & session has a **Show payload** button
(`src/workspaces/Settings.tsx:399-434`) which calls through to `currentPayload` in the main process
and prints the JSON. It is the *real* payload, built by the same shared code and passed through the
same `sanitize`, not a description of one — that is the reason payload construction is pure and lives
in `shared/`. With telemetry on there is also **Send one now**, which ignores the schedule.

**Sending.** Facts accumulate in memory during a run (`electron/telemetry.ts:20-50`) and are sent at
most once every three days (`electron/telemetry.ts:18`). `maybeSend`
(`electron/telemetry.ts:90`) runs once, 20 seconds after startup (`electron/main.ts:375`), and does
nothing at all unless telemetry is on and enough time has passed. Nothing is queued to disk: a failed
send is lost, which is the right trade for data this unimportant.

**Server side**, the endpoint is rate-limited per IP (120/hour), requires an `install` value matching
`/^[0-9a-f-]{8,64}$/i`, and has a global cap of 200,000 rows per 24 hours
(`site/app/api/telemetry/route.ts:61-86`). Over the cap it answers `204` and drops the report
silently — a counter is not worth an error budget.

## Adding a paid feature

`Feature` (`shared/license.ts:23`) and `hasFeature` (`shared/license.ts:100`) exist and work, and
**nothing gates on them today**. Free carries no features, and every capability SPYDIR currently has
is available to everyone. To add one:

1. Add the name to the `Feature` union in `shared/license.ts:23`. It is a shared type, so the app,
   the server payload and the reserved-keys script all describe the same set.
2. Put it on the licence rows that should have it — the `features` column is a JSON array
   (`site/lib/server/store.ts:42`) and is passed straight into the signed payload
   (`site/app/api/activate/route.ts:82`). Reserved keys get theirs from `PLAN`
   (`site/scripts/reserved-keys.mjs:22-25`).
3. Gate the capability with `hasFeature(licence, 'your-feature')` in the renderer, reading `licence`
   from `useApp()`. Note that `hasFeature` returns `false` for a `lapsed` licence regardless of what
   the payload says, which is deliberate and is the only consequence lapsing has.

Two constraints are worth keeping in mind. The gate is only as good as the signature check: a
feature list is trustworthy because it was signed (`electron/license.ts:59`), so a build that cannot
verify signatures must not be treated as entitled to anything. And the existing statuses should keep
their meaning — `grace` exists so that an offline machine does not lose what it paid for, so gating
on `status === 'active'` instead of using `hasFeature` would quietly reintroduce the locked door this
design avoids.

## What production refuses to start without

`requireProductionEnv` (`site/lib/server/env.ts`) is called at the top of every route and throws on
the first request if any of these is missing or implausible. Each had a development fallback that let
the server answer `200`s while doing something quietly wrong.

| Variable | Requirement | Without it |
| --- | --- | --- |
| `LICENSE_PRIVATE_KEY` | PKCS#8 PEM | Every activation is signed by a key generated at boot; no installed copy can verify it and a restart invalidates every licence issued |
| `LICENSE_PEPPER` | ≥ 32 random characters | Machine identifiers are hashed with a value published in the source, and are reproducible by anyone holding the database |
| `LICENSE_SECRET` | ≥ 32 random characters, different from the pepper | Stored licence keys are encrypted with the pepper, so one leak does both jobs |
| `LICENSE_DB` | Absolute path outside the deploy tree | A deploy can erase the licence database |
| `TRUST_PROXY_HOPS` | 1–9 | Client addresses cannot be told from ones the caller typed into `X-Forwarded-For`, and every rate limit collapses into a single shared bucket |

The database is SQLite in WAL mode, created `0700` with the database and its two sidecar files
`0600` (`site/lib/server/store.ts:16-34`). It holds every registered address and a decryptable key
for each, which is the reason for the modes.

## Tests

**`tests/license.test.ts`** covers the shared contract, which is the piece both sides depend on:

- `normalizeKey` against every arrival form — surrounding whitespace, lowercase, a line break
  mid-key, a non-breaking space, no dashes, and no prefix — all collapsing to one string; that it is
  idempotent, so normalising twice cannot corrupt a key; and that it does not invent a key out of an
  empty or nonsense string.
- `keyLooksValid` passing a key that only needed tidying, and rejecting the wrong length and the
  excluded letters `I`, `L`, `O`, `U`.
- `tidyKeyInput` stripping whitespace, including a zero-width space, without reformatting.
- `keyHint` showing only the last group and not leaking the first.
- `statusOf` across the whole state machine: active before the check falls due, `grace` at five days
  and at `GRACE_DAYS - 1` past it, `lapsed` at `GRACE_DAYS + 1`, and `lapsed` immediately when
  `expiresAt` has passed. The boundaries are expressed in terms of `GRACE_DAYS` rather than the
  number 21, so changing the constant moves the tests with it.

**`tests/otp.test.ts`** covers the verification flow against a real SQLite database in a temp
directory rather than a mock — the attempt cap and the expiry both live in SQL, and a mock would
happily agree with a broken query. It asserts that codes are six digits; that the code itself is
never stored and the stored value is a SHA-256 hex digest; that asking again replaces the live
challenge rather than adding a second, and invalidates the previous code; that the send cap stops
issuing; that a correct code is accepted and then consumed, so it cannot be replayed; that wrong
attempts count down and then destroy the challenge, taking the correct code with it; that a code is
useless against a different address; that an expired code is refused; that checking an address with
no challenge behaves like an expired one rather than erroring; and that `pruneCodes` clears expired
rows and leaves live ones.

`tests/telemetry.test.ts` sits alongside these and covers the payload itself: that it carries nothing
identifying, that sizes are ranges rather than counts, that workspaces are deduplicated and sorted,
that a run with no directory opened still produces a valid payload, and that `sanitize` drops
anything a caller adds.
